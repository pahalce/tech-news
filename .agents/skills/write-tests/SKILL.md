# Write Tests

## Quick Start

1. 実装前に「〜したとき、〜となる」形式でテストケースを列挙する。
2. 1ケースにつき1テストを作る。
3. 各テストは Arrange-Act-Assert の3フェーズに分け、コメントで区切る。
4. 1テスト1アサーションを原則とする。
5. テスト名は仕様として読める文章にする。
6. テスト間での共通化（共通fixture/共通ヘルパー）は原則避け、各テストが独立して読めるようにする。
7. 「〜したとき、〜となる」命名ルールは `it`（テストケース）に適用し、`describe` は「〜に関するテスト」のような対象ベース命名でよい。

```ts
it("無効な入力を渡したとき、バリデーションエラーになる", () => {
  // Arrange
  const input = "";

  // Act
  const actual = validateInput(input);

  // Assert
  expect(actual.ok).toBe(false);
});
```

## Principles

- テストは設計行為: テストを書くことで、使いやすいAPIを設計する。
- テストは仕様書: テストコードを最も正確なドキュメントとして扱う。
- ふるまい中心: 実装詳細ではなく、公開インターフェースの結果を検証する。
- 小さく進める: 1テストずつ追加し、失敗→実装→成功を短く回す。
- 独立性重視: 各テストは単体で意味が通るように書き、テスト間の隠れた依存を作らない。

## Workflow

### 1) 事前に仕様を列挙する

- [ ] 実装前に、期待するふるまいを「〜したとき、〜となる」で列挙したか
- [ ] 優先順位をつけて、最小の1ケースから着手するか
- [ ] ケースがAPI利用者視点で書かれているか

### 2) 1テストを設計する

- [ ] テスト名が仕様文になっているか
- [ ] 1テスト1アサーションになっているか（必要ならテストを分割）
- [ ] 単一の関心事だけを扱っているか
- [ ] そのテスト単体で Arrange が完結しているか（他テスト用ヘルパーに依存しすぎていないか）
- [ ] `describe` は対象/責務でグルーピングされ、`it` が「〜したとき、〜となる」になっているか

### 3) AAAで実装する

各テストで必ず次のコメントを入れる:

```ts
// Arrange
// Act
// Assert
```

- Arrange: 前提・入力・依存データを準備する
- Act: 対象APIを1回呼ぶ
- Assert: 観測可能な結果を1つ検証する

### 4) 設計を見直す

テストを書いていて次が起きたら、API設計を改善する:

- Arrange が長すぎる: 生成APIやデフォルト値を見直す
- Act が複雑: 公開APIの責務を分割する
- Assert が曖昧: 戻り値やエラー表現を明確にする

## Review Checklist

- [ ] すべてのテストが「〜したとき、〜となる」で説明できる
- [ ] `describe` は「〜に関するテスト」など対象ベースで整理されている
- [ ] すべてのテストに Arrange / Act / Assert コメントがある
- [ ] 1テスト1アサーションを守れている
- [ ] テスト間の共通化に頼らず、各テストが独立して読める
- [ ] 実装詳細ではなく公開インターフェースを検証している
- [ ] テストを読むだけで仕様が理解できる
